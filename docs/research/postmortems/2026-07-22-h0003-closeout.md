## 1. What blocked, precisely, and why it is the correct outcome

G1 (hash) and G2a/G2b (key uniqueness, null checks, station/variable
sets) all passed. **G2c (point-in-time integrity) failed on exactly 2
of 362 rows:**

| station | variable | target_date | issue_time | "settled" issuance time |
|---|---|---|---|---|
| DEN | tmax_f | 2026-07-22 | 2026-07-22 18:46:34 | 2026-07-22 12:31:00 |
| DEN | tmin_f | 2026-07-22 | 2026-07-22 18:46:34 | 2026-07-22 12:31:00 |

Root cause: `target_date = 2026-07-22` is **the day this study was
executed** — still in progress, not yet over. DEN had received exactly
one same-day CLI observation issuance for that date (a same-day partial
reading at 12:31 UTC) by execution time. The reused `_settled_observations`
convention ("settled" = latest available issuance) correctly identifies
that 12:31 reading as the *latest so far* — but for an in-progress day,
"latest so far" is not a finalized truth; a genuine final report (the
next-morning CLI, per H0002/H0011/H0013's own established finding)
had not yet been issued. A forecast fetched later the same day
(18:46 UTC) therefore appears, mechanically, to postdate its own
"settlement" — exactly the point-in-time violation G2c exists to catch.

**This is the gate working as designed, not a bug in the analysis.**
The pre-registration's `_settled_observations` reuse (justified in
§2 as the correct convention for pure forecast verification, as
opposed to `value_at_settlement`) is sound for a target date that has
actually concluded; it is unsound for the current in-progress day,
and the pre-registration did not make "target_date has fully
concluded" an explicit inclusion criterion. That gap is the actual
finding here, and it is exactly the kind of defect a frozen,
pre-registered integrity gate is supposed to surface *before* a
result is computed — not after.

**No fix was applied and no re-run was attempted.** Per the task's own
requirement ("if assumptions fail, block according to the
pre-registered rules"; "no changing hypotheses after pre-registration"),
loosening G2c or silently excluding these two rows mid-execution to
force a passing run would be exactly the p-hacking this protocol
exists to prevent. The honest result is BLOCKED, on both tracks (Track
A and Track B share the same integrity gate sequence, so a G2c failure
blocks both by the design's own construction — not a duplicated bug).

## 3. Interpretation

H0003's first execution produced two honest, useful, non-fabricated
facts: (1) the forecast archive does not yet support *any* tier of this
study, exactly as anticipated in the frozen document before execution;
and (2) the "settled = latest issuance" truth convention, reused
verbatim from the platform's existing dataset-builder code, has a
real edge case at the current-day boundary that a future execution
(or that convention's use elsewhere) should account for explicitly.
Neither fact is a failure of the study design — both are exactly the
kind of finding a rigorous, gated protocol is supposed to produce on
sparse or edge-case data, rather than silently producing a misleading
number.

## 4. Recommendation for the retry (a new, explicitly amended execution)

Do not retry before accrual is adequate (§8 already estimated this at
roughly 90 days from 2026-07-20, i.e. ≈ 2026-10-18, for Track B; Track
A's lighter floors may be reachable somewhat earlier — the next
execution's own gate report will show the achieved N rather than a
projection this document cannot support). When retried, the
pre-registration for that execution should explicitly add, as a named
inclusion criterion (not a silent patch to this one): **a target_date
is eligible only once its observation has received a genuinely final
report** — operationalized, per the program's own established
convention (H0002/H0011/H0013), as an issuance timestamped after local
midnight following the target date, not merely "the latest issuance
seen so far." This closes the exact gap G2c caught here. This
recommendation is offered for the *next* pre-registration to adopt
explicitly; it is not applied retroactively to this one.

   same-issuance-batch; this is a single edge case (today's date), not
   a broad pattern across the 362-row extract — but it is a structural
   inevitability of running any such study on the day of, or the day
   after, a still-open target date, which the next execution's
   eligibility criterion should close for good.
2. **No error statistic exists to critique.** This closeout reports
   process and gate findings only; there is no forecast-error
   conclusion of any kind to qualify further.
3. **The 90-day (Track B) / lighter Track A floors are estimates**,
   not guarantees, of when a retry will succeed; actual accrual
   depends on the collector's real issuance rate per day, which this
   document cannot project from two days of history.

   of this; it remains open, unconfirmed, and unrejected, awaiting
