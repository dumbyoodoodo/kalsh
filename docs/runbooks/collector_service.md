# Runbook: Collector background service (macOS launchd)

Runs `kalshi-weather ops run` (Kalshi + weather + price-sync collectors in one
supervised process — see `docs/runbooks/operations.md`) as a native macOS
launchd user agent: starts at login, restarts on unexpected exit, rotates its
logs, and refuses to start when the environment it depends on is broken.

## Layout

| Piece | Where |
|---|---|
| Service plists (generated at install) | `~/Library/LaunchAgents/com.kalshi-weather.collector.plist`, `…logrotate.plist`, `…monitor.plist` |
| Entry point / preflight / rotation | `scripts/service/run.sh`, `preflight.py`, `rotate_logs.sh` |
| Logs (internal disk, deliberately not on the SSD) | `~/Library/Logs/kalshi-weather/collector.{out,err}.log` (+ `.1`–`.5` rotations; override dir with `KALSHI_LOG_DIR` in `.env`) |

The same installer also manages a fourth agent, `com.kalshi-weather.monitor`
-- a scheduled data-quality check with alerting, not another collector; see
`docs/runbooks/monitoring_alerting.md` for that one specifically.

The plists are **generated by the installer** with this checkout's absolute
paths — nothing machine-specific is committed. Environment (credentials,
`KALSHI_DATA_DIR`, DB URL) comes from the repo's `.env` via `Settings`, never
from the plist, so secrets stay out of launchd's domain.

## Commands

```bash
scripts/service/install.sh    # install or reinstall (idempotent), then starts
scripts/service/uninstall.sh  # stop gracefully + unregister; keeps logs & data
scripts/service/restart.sh    # kill + immediate fresh start (use after upgrades)
scripts/service/status.sh     # launchd state, process count, log tail, ops health
scripts/service/logs.sh       # follow logs live;  logs.sh -n 200  for last 200
scripts/service/check_restart.sh            # does the running collector need a restart?
scripts/service/check_restart.sh --restart  # ...and perform it (graceful) if so
```

Manual equivalents: `launchctl print gui/$UID/com.kalshi-weather.collector`,
`launchctl kickstart -k gui/$UID/com.kalshi-weather.collector`,
`launchctl bootout gui/$UID/com.kalshi-weather.collector` (stop until next
install/login).

## Behavior

- **Start**: at login (`RunAtLoad`) and immediately on install.
- **Restart policy**: `KeepAlive.SuccessfulExit=false` — a crash or preflight
  failure (nonzero exit) is retried every ≥60s (`ThrottleInterval`); a graceful
  stop (SIGTERM → `ops run`'s signal handler → exit 0) stays stopped.
- **Preflight (fail loudly)**: before the collector starts, `preflight.py`
  verifies the data root is mounted and writable (`ensure_dataset_root`), demo
  credentials load (never printed), and Postgres answers `SELECT 1`. Any
  failure logs a `PREFLIGHT FAIL: …` line to `collector.err.log` and exits 1 —
  launchd retries, so "Docker not up yet after reboot" self-heals when it is.
- **Single instance**: launchd enforces one run per label, and the launcher
  (`launch.py`) additionally holds a kernel `flock` on
  `<log dir>/collector.lock` inside the collector process itself — released
  by the kernel at the instant the process exits, however it exits. A second
  start waits up to 90s (covering a predecessor's graceful drain during
  restart), then exits 1 so launchd retries later. Note a collector started
  *manually* (`ops run` in a terminal) bypasses the launcher and its lock —
  don't do that while the service is installed; `status.sh` warns if it ever
  sees more than one instance.
- **Log rotation**: copytruncate at >20 MB, keeping 5 generations; runs at
  every service start and every 6h via the `…logrotate` agent (launchd
  `StartInterval`, not cron). A few lines can be lost at the copy/truncate
  boundary — operational logs only; the scientific record is in Postgres.

## One-time macOS privacy (TCC) grants

Background (launchd-spawned) processes don't inherit Terminal's file-access
grants. Two placements matter here:

- **Repo location**: `~/Documents`, `~/Desktop`, `~/Downloads` are
  TCC-protected; a launchd agent whose code lives there is silently denied
  (`Operation not permitted`, exit 126). This repo therefore lives at
  `~/dev/kalsh` (moved 2026-07-21), outside protected folders.
- **External SSD** (`KALSHI_DATA_DIR` on `/Volumes/…`): first background
  access triggers a blocking "python3.12 would like to access files on a
  removable volume" consent — approved once (2026-07-21), persisted per
  binary. If the uv-managed Python is ever replaced (new interpreter path),
  expect the prompt once more; a preflight that hangs >60s is the symptom
  (System Settings → Privacy & Security → Files and Folders → python3.12).

## Upgrade procedure

```bash
cd ~/dev/kalsh
git pull                      # or apply changes
uv sync                       # if dependencies changed
PYTHONPATH=src .venv/bin/pytest -q
scripts/service/check_restart.sh   # tells you: nothing / restart.sh / install.sh
scripts/service/restart.sh    # picks up new code; .env changes too
```

Re-run `scripts/service/install.sh` instead of `restart.sh` if anything under
`scripts/service/` or the plist settings changed, or if the repo moved (the
installer regenerates paths).

Not sure whether the running collector already has the current code? At every
start the service records a manifest of what it launched with
(`<log dir>/collector.manifest.json` — git commit plus content hashes, never
file contents). `scripts/service/check_restart.sh` diffs the working tree
against it and answers "Collector restart required" / "not required" /
"REINSTALL required", with the changed files and per-file reasons;
`--restart` then performs the graceful restart (or reinstall) it recommended.
Which paths demand which action is defined in one place:
`src/kalshi_weather/ops/restart_policy.py` (summarized in
`docs/runbooks/operations.md`, "Collector restart policy").

## After a reboot

Nothing to do in the normal case: the agent starts at login, preflight fails
while Docker Desktop/Postgres are still coming up, and launchd's 60s retry
loop starts the collector as soon as `SELECT 1` succeeds. Verify with
`scripts/service/status.sh`. If the SSD wasn't mounted at login, preflight
keeps failing with the "is the drive mounted?" error until it appears — plug
it in and the next retry proceeds.

## Verifying continuous collection

`scripts/service/status.sh` shows the essentials: exactly one collector
process, launchd `state = running`, and `ops health`'s per-collector
freshness (`[ok]` vs `[STALE]`, newest snapshot/observation timestamps).
For a deeper check, `scripts/service/logs.sh -n 50` should show
`collector.cycle_complete` lines with nonzero `*_duplicate` counters —
duplicate detection working is the signature of append-only collection
overlapping correctly with already-stored history.

## Reboot / power-loss recovery

After a reboot or power loss the whole stack must come back **without a
human**, in dependency order: Docker → Postgres → collector. The 2026-07-26
incident (`docs/incidents/2026-07-26-power-loss-collection-gap.md`) was caused
by gaps in this chain. Checklist:

1. **Postgres returns with Docker** — `docker-compose.yml` sets the Postgres
   service to `restart: unless-stopped`. On an already-running container that
   predates that line, apply it live once with
   `docker update --restart unless-stopped kalsh-postgres-1`. Verify:
   `docker inspect kalsh-postgres-1 --format '{{.HostConfig.RestartPolicy.Name}}'`
   → `unless-stopped`.
2. **Docker itself starts at login** — enable Docker Desktop → Settings →
   General → "Start Docker Desktop when you sign in". Without this the DB never
   comes up and the collector will restart-loop against an unreachable DB
   (harmlessly, but collecting nothing).
3. **The host reaches a logged-in session** — the collector runs as a launchd
   **LaunchAgent** (`RunAtLoad=true`), which starts at *login*, not at boot. If
   the machine reboots to a locked login screen with nobody signed in, nothing
   starts. Enable macOS auto-login (System Settings → Users & Groups →
   Automatically log in as) if the host is a dedicated collector box.
   (FileVault blocks auto-login; a collector host typically shouldn't use it.)
4. **The host powers back on after a power cut** — desktop Macs only: System
   Settings → Energy → "Start up automatically after a power failure" (or
   `sudo pmset -a autorestart 1`). Laptops have a battery and this setting does
   not apply; the lid/charger governs power-on instead.
5. **Something off-device notices if any of the above fails** — the external
   heartbeat (`docs/runbooks/monitoring_alerting.md`, "External uptime
   heartbeat"). On-device alerting cannot fire while the host is off.

None of steps 2–4 are code and none can be set from this repo; they are host
settings recorded here so the recovery posture is auditable. Steps 1 and 5 are
enforced by this repo (compose restart policy; heartbeat agent).

## Startup rate-limit grace (restart-only Kalshi 429)

**Root cause.** Every collector restart produced exactly one immediate Kalshi
cycle that failed with HTTP 429 (`too_many_requests`) at `requests_attempted=0`,
followed by a fully successful cycle. Steady state already runs at Kalshi's rate
ceiling (~110+ short-backoff 429 retries per cycle, all absorbed and non-fatal),
but a cold-started process fires its *cycle-critical discovery* request with a
fresh throttle immediately after launch, while the rate window is still hot from
the just-killed prior process. The discovery request exhausts its short retry
budget (3 attempts) and aborts the whole first cycle — whereas the same 429 on a
per-market request in steady state is tolerated. It always self-recovered on the
next cycle with no lasting data impact.

**Fix.** `KALSHI_STARTUP_GRACE_SECONDS` (default 10s) applies a single bounded,
interruptible pause before the Kalshi loop's **first** cycle only. It lets the
rate window clear before the cold discovery request. It never changes
steady-state cadence or throughput (subsequent cycles are unaffected), and the
separate weather loop starts immediately. Set 0 to disable.

**Expected operator log on restart:** one
`collector.startup_grace seconds=10.0 reason=avoid cold-start kalshi
rate-limit collision on first cycle` line, then a normal
`collector.cycle_complete` for the first Kalshi cycle.

**Intentional startup deferral vs outage.** The `collector.startup_grace` log +
a *successful* first cycle is the intended, healthy path. A *persistent* 429
across multiple full cycles, or a 401/403, is NOT this — it indicates a real
rate-budget/auth problem (another credential consumer, or a genuine limit) and
should be investigated, not masked by a longer grace.

**Rollback.** Revert the startup-grace commit (or set
`KALSHI_STARTUP_GRACE_SECONDS=0`) and restart only the collector. The change is
timing-only: no schema, no data, no request-handling change.
